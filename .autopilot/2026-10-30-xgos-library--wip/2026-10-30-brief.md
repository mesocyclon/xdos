## Исходная постановка архитектуры, дословно

Ты — главный архитектор Go-систем. Спроектируй архитектуру библиотеки на Go
для генерации Word-документов (.docx) с нуля, редактирования любых их частей,
вставки одного документа в другой и экспорта в PDF без внешних программ
(без LibreOffice, headless-браузеров, cgo и т.п.).

ФОРМАТ ОТВЕТА
Только архитектура: без реализации. Допустимый код — только объявления
Go-интерфейсов, ключевых типов (сигнатуры) и дерево пакетов. Без тел функций.

ПОДХОД
Тонкий типизированный API поверх сохраняющего XML-дерева (идея python-docx,
но идиоматично для Go): неизвестные элементы и атрибуты хранятся как есть и
записываются обратно без потерь. Не копируй Python-специфику (динамические
прокси, монки-патчинг); используй композицию, встраивание, generics,
functional options, iter.Seq, context, io.ReaderAt/io.Writer.

ТРЕБОВАНИЯ
1. Слои и пакеты: OPC/ZIP (части, relationships, content types) → XML-DOM с
   сохранением неизвестного → доменный API (Document, Section, Paragraph, Run,
   Table, List, Image, Header/Footer, Footnote, Field) → стили → layout → PDF.
   Покажи граф зависимостей (строго однонаправленный).
2. Стили: каскад docDefaults → стиль таблицы → абзаца → символа → прямое
   форматирование; отдельный resolver; кэш вычисленных значений.
3. Редактирование: адресация узлов (стабильные ID/пути), запросы и обход,
   транзакционные команды с undo/redo, валидация схемы OOXML.
4. Вставка документа в документ: слияние styles, numbering, media,
   relationships и ID с разрешением конфликтов (стратегии: reuse/rename/remap);
   сохранение разделов, колонтитулов, закладок и ссылок.
5. PDF без сторонних программ: собственный layout-движок (шрифты и
   метрики, subsetting, переносы, разбиение на страницы, таблицы, колонтитулы,
   сноски, изображения) и PDF-writer. Определи границу между layout и writer
   интерфейсом, чтобы можно было подменить любую часть. Опиши, какие
   возможности входят в v1, а какие нет, и как это влияет на точность.
6. Возможности Go: горутины и errgroup для параллельного разбора частей,
   потоковая запись, sync.Pool, ленивая загрузка медиа, контексты и отмена,
   неизменяемые снимки для безопасного чтения, минимум аллокаций.
7. Расширяемость: плагины через интерфейсы (кастомные элементы, фильтры,
   шрифтовые провайдеры), опции конфигурации, чёткая модель ошибок.
8. Тестирование: roundtrip docx→docx, golden-файлы, корпус реальных
   документов, fuzzing парсера, бенчмарки.

ЧТО ВЕРНУТЬ
- Дерево пакетов и граф зависимостей.
- Интерфейсы и ключевые типы по каждому пакету (только сигнатуры).
- Потоки данных: чтение, редактирование, слияние, экспорт в PDF.
- Таблицу архитектурных решений: решение / альтернативы / причина выбора.
- Риски (в первую очередь layout и PDF) и этапы реализации.
- Что осознанно не поддерживается и почему.

Не пиши общих рассуждений. Если информации не хватает — явно укажи допущение.

## Последующие указания пользователя, дословно

> Расход памяти и вычислений должен быть обоснован объёмом обрабатываемых данных и выполняемой операцией. Понятные границы подсистем и зависимости, единая модель данных, исправление общей причины без дублирования и частных обходов. Изменения внутри подсистемы должны затрагивать минимум несвязанного кода.

> Структура каталогов и Go-пакетов должна отражать ответственности подсистем. Разбиение должно обеспечивать понятную навигацию и направленные зависимости

> Вернуть полноценный раздел merge: стратегии reuse/rename/remap, таблица конфликтов по типам частей, обработка секций, колонтитулов и закладок. Сократить остальное.

> Добавить слой простого API (docx.New, doc.AddParagraph, p.AddRun) поверх edit, плюс сквозной пример на 10 строк.

> Упростить lifetime: неизменяемые снимки с GC, Close только у источников.

> Сократить документ втрое: оставить дерево пакетов, граф, интерфейсы, потоки данных, таблицу решений, риски, этапы, список «не поддерживается».

> Для PDF: сделать v1 осмысленным, добавив хотя бы приблизительный autofit с предупреждением вместо отказа. Бандлить дефолтные шрифты. Начать этапы со spike по subsetter и shaping. Ввести количественную метрику на корпусе.

> Определить границы Commit-валидации: валидировать целиком на Save, а при Commit — только быстрые инварианты (по OPC и ссылкам).

> docx.New, doc.AddParagraph, p.AddRun сказаны как пример, очевидно что это не только 3 функции

## Зафиксированный исходный артефакт

`architecture-baseline.md` — точная копия текущего architecture.md на начало реализации: 549 строк, SHA-256 `5d3eba60a89dacd814f644648b5f18be0a2834a4ce1c75c91d7cb16d769c3d13`. Это технический артефакт, а не дословная речь пользователя. Слова «по архитектуре» относятся к нему. Правки архитектуры в текущем прогоне пока не выполнены.

Текущее подтверждение перехода к реализации заменяет прежнее ограничение «только архитектура» для новой задачи. Объём v1 и явно неподдерживаемые возможности берутся из зафиксированной архитектуры; никакая частичная стадия не считается выполнением полной библиотеки. Разработка начинается после двух согласований manual: спецификация, затем план.

На диске при старте был только architecture.md; старые .autopilot отчёты и исходный brief отсутствовали. Текст выше восстановлен из разговора; никаких результатов реализации или старых runtime-проверок не подразумевается.
